# STM32 串口 ISP 烧录 + 串口监视

> 一根 USB-TTL 干两件事：**烧录**（编译 → 转 bin → 找串口 → 扫波特率 → 握手 → 烧）
> 和**看打印**（带时间戳、可存日志、掉线自动重连）。
> 不用 ST-Link，也不用再单独开一个串口助手。

## 为什么是一根线

20 块钱那种 **ST-Link V2 没有虚拟串口**。你用它烧完，想看板子的 `printf`，
还得再插一根 USB-TTL —— 桌面上两根线，两个驱动，两个可能抢串口的程序。

USB-TTL 一根线两用：烧录用它，看打印也用它。烧完关掉烧录窗口，`monitor.bat` 接着看，
中间不用拔插、不用换口。

（带虚拟串口的 ST-Link V3 / 板载 V2-1 确实能一根线搞定，但那是另一个价位。
手头已经有一根 CH340 的话，这套工具就是为它写的。）

## 它解决什么（烧录）

STM32 用串口 ISP 烧录，本身不复杂：BOOT0 拉高 → 复位 → 发 `0x7F` → 收到 `0x79` → 烧。
但在**面包板 + 长杜邦线**上，这套流程会以各种方式失败，而且失败时的报错基本没用。

这个工具把这些坑一个一个填了：

### 1. 波特率不是越高越好，也不是固定的

坏消息：同一个板子，昨天能烧的波特率今天可能就不行。
分布电容、线长、接触电阻都会影响，**没有一个"正确"的波特率**。

所以这里的做法是**扫描**：按 `38400 → 19200 → 9600` 依次试，
**找到能握手的那个，再用它烧**。而不是死磕一个波特率反复重试。

> 作者在「面包板 + 20cm 杜邦线」上的实测：
> 38400 烧 27 KB 约 7 秒，19200 约 15 秒，9600 约 30 秒，**115200 从未成功过**。
> （这是开发时的记录，不是严格的基准测试。）

### 2. 握手可以"批量轰炸"，不用发一个等一个

这是整个工具里最有用的一招。

STM32 的 bootloader 只要收到**一个完整的 `0x7F` 字节**就会回 `0x79`。
这意味着你根本不需要"发一个 → 等回应 → 超时 → 再发一个"，
完全可以**连发一批，再一次性读**：

```python
for _ in range(BATCH):        # 连发 8 个 0x7F
    s.write(b"\x7f")
    time.sleep(0.01)
time.sleep(0.04)
r = s.read(64)                # 一次性读，只要里面有 0x79 就算握手成功
```

避开了每次读超时的等待，**握手速度翻倍**。而不稳定线路上，
"能不能在有限次尝试内握上手"往往就是"能不能烧进去"的全部。

### 3. 串口被占用 —— 烧录失败的头号原因，但报错完全看不出来

串口助手没关、上一次的烧录窗口没关，都会让烧录脚本打不开串口。
底层抛出来的异常看不出是这个原因。

这里在开烧之前**先试着独占串口**，失败重试 3 次，然后明确告诉你该关什么：

```
★★★ 串口被占用了！打不开 COM7

★★ 这是烧录失败的常见原因，请检查：
   1. 串口助手 / 串口监视器还开着吗？ → 关掉它
   2. 上一次的烧录窗口没关？        → 关掉
   3. 别的东西占着这个 COM 口？      → 关掉
```

### 4. 烧录阶段失败就降速重试

握手成功的波特率烧到一半失败，会自动往下降档重试（38400→19200→9600→4800）。

### 5. 连不上时，提示具体到线

```
检查：
  1. BOOT0 是不是在【1】
  2. 按过复位键吗（★ 边看屏幕边按，不要停）
  3. USB-TTL 三根线（TXD->A10、RXD->A9、GND->G），试试把 TXD/RXD 对调
  4. 模块的线全拔掉（只留 USB-TTL）
  5. 杜邦线换成短的
```

## 串口监视

`monitor.bat` 是同一个仓库里的第二个工具，用同一根线、同一个 COM 口。

| | 说明 |
|---|---|
| 自动找口 | 认 CH340 / CP210x / FT232；多个串口认不出时用 `--list` 看一眼 |
| 时间戳 | 每行前面加 `[HH:MM:SS.mmm]`，抓时序、对齐事件用得上 |
| 存日志 | `--log run.log` 追加写入，跑通宵也不会丢 |
| 掉线重连 | 板子复位、线松了会自动重连，不用重启脚本 |
| 中文不乱码 | 按 UTF-8 解，坏字节用替代符，不会整行崩掉 |

```bash
monitor.bat                          # 自动找口，115200
monitor.bat --port COM7 --baud 9600  # 指定口和波特率
monitor.bat --log run.log            # 顺便存日志
monitor.bat --list                   # 只列出串口
```

> 为什么不用串口助手：串口助手是独占的，看打印的时候不能烧，烧的时候不能看，
> 而且每次都要手动选口、选波特率。这两个脚本共用一套找口逻辑，切换就是"关一个开一个"。

## 安装

```bash
pip install -r requirements.txt     # pyserial + stm32loader
```

Keil 的 `UV4.exe`（命令行编译）和 `fromelf.exe`（把 `.axf` 转成 `.bin`）会**自动探测**：
先看环境变量，再读 Keil 的注册表项，最后扫常见安装目录。装在非常规位置就自己指定：

```bat
set KEIL_ROOT=D:\你的Keil目录
:: 或者分别指定
set KEIL_UV4=D:\Keil_v5\UV4\UV4.exe
set KEIL_FROMELF=D:\Keil_v5\ARM\ARMCLANG\bin\fromelf.exe
```

> 探测时踩过一个坑，写在这里省得别人再踩：
> Keil 注册表 `HKLM\SOFTWARE\WOW6432Node\Keil\Products\MDK` 的 `Path` 值
> 指向的是 `<Keil根>\ARM`，**不是 Keil 根目录**。
> 所以代码里既把它当根试，也把它的父目录当根试。

## 使用

### 完整流程（编译 + 烧录）

```bash
flash.bat
```
```
  找到这些工程：

    [1]  01_uart
    [2]  02_esp_link
    [3]  03_i2c_scan
    ...

  选哪个？(输入 1~3，直接回车 = 1): 1

  工程：step1_uart.uvprojx
  [1/4] 编译
  [2/4] 生成 .bin
  [3/4] 找串口
  [4/4] 烧录

  ★★ 请先做好：
       1. BOOT0 跳线帽拨到【1】那边
       2. 按一下复位键（RST）

  ★ 接下来：
       屏幕会飞快地试（每 50 毫秒一批），你【看着屏幕按复位键】
       一旦握上手，立刻自动开始烧录

  做好了按回车，开始...
```

### 命令行选项

**flash.py**

| 选项 | 作用 |
|---|---|
| `--port COM3` | 指定串口（默认自动找 USB-TTL） |
| `--baud 115200` | 只用这个波特率，不扫描 |
| `--no-build` | 跳过编译，直接用上次生成的产物 |
| `--bin app.bin` | 完全不碰 Keil，直接烧一个现成的 bin |
| `-y` | 跳过"按回车开始"的确认 |

**monitor.py**

| 选项 | 作用 |
|---|---|
| `--port COM3` | 指定串口（默认自动找 USB-TTL） |
| `--baud 115200` | 波特率，默认 115200 |
| `--log run.log` | 输出同时追加写入文件 |
| `--list` | 只列出串口 |
| `--no-reconnect` | 掉线就退出，不自动重连 |

## 硬件接线

```
USB-TTL           STM32F103
  TXD  ──────────  A10  (USART1_RX)
  RXD  ──────────  A9   (USART1_TX)
  GND  ──────────  GND
                     ↑ 共地是必须的
BOOT0 ── 跳线帽拨到 1，复位，烧完拨回 0 再复位
```

> **烧完之后 `BOOT0` 拨回 `0` 并再按一次复位，程序才会跑。** 这两步漏了会很迷惑：
> 烧录显示成功，板子却毫无反应。

## 和 ST-Link / 其他工具比

| 工具 | 强在哪 | 代价 |
|---|---|---|
| **ST-Link V2（20 元款）+ Keil F8** | 烧录最快，三秒，不用拨 BOOT0 | **没有虚拟串口**——烧完想 `printf` 还得另插一根 USB-TTL，多占一个 USB 口、多一个驱动 |
| **ST-Link V3 / 板载 V2-1** | 一根线同时搞定烧录 + 虚拟串口 | 价格或板子条件不同；本项目没在这些型号上测过 |
| `stm32flash` / CubeProgrammer CLI | 成熟工具，支持全系列 | 它们**假设链路是通的**；链路不稳时报错帮不上忙，也不带波特率扫描和串口监视 |
| 各种串口 ISP 上位机 | 图形界面，点点就行 | 要手找 hex、手切波特率，且和串口助手抢同一个口 |

**这套工具针对的场景很具体**：手头只有 USB-TTL、板子在面包板上、线还挺长，
而且要一边烧一边看打印。它不打算取代 ST-Link，只是让"没有 ST-Link"这件事不那么难受。

## 已知限制

- 只自动识别 CH340 / CP210x / FT232 这几类 USB-TTL，其他芯片用 `--port` 指定
- 只在 Windows 上测过（用了 Keil 的命令行和 Windows 注册表）
- `--bin` 模式不校验 bin 是不是对这块板子的
- 波特率扫描的上限是 38400，没往上试——**在不稳定线路上更高也没意义**
- `monitor.py` 只负责"看"，不做发送/交互（要发命令还是得用串口助手）

## 背景

这个工具是在做一块 STM32 开发板（[健康监测设备](https://github.com/Beiyiovo/stm32-health-monitor)）的
过程中长出来的，前后改了很多轮。源码注释里保留了演进轨迹：

- **早期**：直接调 `stm32loader` 反复重试 → 一直不稳定
- **转折**：回到"先用 Python 直接发 `0x7F` 扫波特率、找到能握手的、再用它烧"
- **优化**：握手改成批量轰炸；烧录失败自动降速；新增串口占用检测
- **后来**：把 `serial.bat` 升级成带时间戳、日志、自动重连的 `monitor.py`

> **最大的教训**：**先确认物理链路能握手，再谈烧录。**
> 跳过握手直接烧，失败时根本分不清是线的问题、波特率的问题、还是串口被占用的问题。
